# AGENTS.md

Notes for AI coding agents working on this repository. Read this before making changes. README.md covers setup and settings for people; this file covers rules and lessons learned that are easy to get wrong.

## Project summary

Riverside Town is a Roku screensaver written in BrightScript with SceneGraph. It shows a town beside a river with mountains behind it. Five scenery layers scroll at different speeds (parallax), up to eight cars drive in two lanes, and a panel shows the time, temperature, and weather from the Open-Meteo API. The town (buildings, names, colors, fonts, animals, weather location, units, and extras) comes from `town.json`, so anyone can make their own town. The scene switches between day, dusk, and night palettes based on the real sunrise and sunset times, and between four seasons based on the date.

## Writing rules

These apply to code, comments, commit messages, README.md, and this file.

- Keep every file plain ASCII. Do not use em dashes or the Unicode ellipsis character. Use commas, colons, semicolons, or separate sentences instead. If a non-ASCII character must appear in an image, write it as an escape in the generator (for example, `"Luke\u2019s"`). Font license files in `tools/fonts` are an exception: they are copied as they are from the font projects, so they may contain non-ASCII characters. Do not edit them.
- Use plain, literal language. Do not use idioms, figures of speech, or clever phrasing.
- Keep README.md accurate when behavior, settings, or file layout change.

## Roku rules learned on this project

- Do not define `Main()` in `source/main.brs`. Roku requires screensavers to use only `RunScreenSaver()`. If `Main()` exists, Roku treats the app as a normal channel and does not list it under Settings > Theme > Screensavers. The manifest must also keep `screensaver_title` and `screensaver_private=0`.
- Do not mirror a node with a negative scale. Roku does not draw rotating children (the car wheels) correctly inside a group with a negative scale. To make a car face left, the code swaps to a mirrored body image (`car_<name>_left.png`), moves the wheels to `w - x`, and reverses the spin direction. Keep scale values positive.
- Network requests must run in a Task node. `components/WeatherTask.brs` does this with `roUrlTransfer` and the `common:/certs/ca-bundle.crt` certificate file.
- Animation interpolators find nodes by id through `fieldToInterp` (for example, `sedan_car.translation`). Animations created in code are appended to the scene root so the id lookup works. Keep node ids unique.
- The loop variable of a `for each` loop must be untyped. Do not reuse a parameter declared with `as` (for example, `name as string`) as the loop variable. The Roku compiler rejects it with "For-Each index variable must be 'dynamic' type", and the `brighterscript` compiler (`bsc`) does not catch it.
- Label text that is too wide is cut off with "...". When changing font sizes or text, check that the longest expected value (for example, "10:42 PM") fits the label width.
- Roku does not give apps the device's ZIP code. The weather location comes from `town.json`. The generator looks up a ZIP code at build time and writes the coordinates, as text, into `components/town_config.json`. BrightScript reads JSON decimals as single-precision floats, so keep the coordinates as strings there.
- `MainScene.brs` reads `pkg:/components/town_config.json` with `ReadAsciiFile()` and `ParseJson()` in `loadTownConfig()`. Every value has a default there, so the screensaver still starts if the file is missing. When a setting is added to `runtime_config()` in `tools/generate_images.py`, add its default to `loadTownConfig()`.

## Configuration (town.json)

- `town.json` at the repository root is the sample town. It is generic on purpose: no real businesses, people, or references. The template for other people is rorpage/riverside-town-sample. Keep the sample `town.json` in this repository and the one in riverside-town-sample the same, except that this one uses lat and lon so it builds without a network connection.
- `tools/riverside/town.schema.json` describes every field. `tools/riverside/config.py` checks `town.json` against it, fills in defaults, and raises `ConfigError` with a message that names the field. When adding a field or option, update the schema, the defaults in `config.py`, and the town.json reference in README.md.
- Shop presets (`bakery`, `diner`, and the others) are in `PRESETS` in `config.py`. A preset is a shop with options already set; options in `town.json` replace them.
- Building types are in `TYPES` in `tools/riverside/buildings.py`. Each has a width function and a draw function `(spec, x, p, season)`, where `x` is the left edge in its town section. Some types are drawn at the position they had in the original town and moved with `shift()`; their `ORIGIN` is the left edge of that drawing. A new type needs a width, a draw function, an entry in `TYPES`, defaults in `DEFAULTS` in `config.py`, and an entry in the schema.
- `tools/riverside/layout.py` places the buildings in 1920 pixel sections with a margin of 16 pixels at each end, so no building crosses a section edge. At most 5 sections, because each one uses about 4 MB of texture memory.
- `tools/build_town.py` is what the Docker image runs. It copies `manifest`, `source`, and `components` to a temporary folder, generates the town into it, and writes `out/riverside-town.zip`, the same files without a zip in `out/roku`, and `out/previews`. The "Build my town" workflow in the template uploads `out/roku` as a download, not the zip: GitHub zips every download, so uploading the zip would put a zip inside a zip. GitHub's zip of `out/roku` has the manifest at the top level, so it installs on a Roku as it is. If a new top-level folder is needed on the Roku, add it to `PACKAGE` there, to `build.sh`, to the `COPY` lines in `Dockerfile`, and to `.dockerignore`.
- The Docker image is `ghcr.io/rorpage/riverside-town-roku-generator`, published by `.github/workflows/riverside-town-roku-generator.yml` when a tag such as `v1.2.0` is pushed. `action.yml` runs the `:1` image. See "Releases" below.

## Artwork rules

- All images in `images/` are generated by `tools/generate_images.py` from `town.json`. Do not edit the PNG files directly. Change the generator or `town.json` and run `python3 tools/generate_images.py --docs docs` from the repository root.
- The color palettes for day, dusk, and night are in the `P` dictionary in `tools/riverside/art.py`.
- Do not draw people anywhere, as the owner asked. Bikes are always empty and parked. Animals and empty vehicles are fine.
- Do not use the E-gineering (E-g) design system colors or fonts in this project unless the owner asks for them. They were removed on purpose. The removed values were #304C5F, #4F7D9B, #F5653D, and #E9EFF6.
- Each scrolling layer is 1920 pixels wide, and its left and right edges must line up so two copies repeat without a seam. The town layer is one tile for each town section, `town_a` to `town_e`. `buildTown()` in `MainScene.brs` creates the posters in `townStrip`: each section in order, then section A again. The strip slides by the number of sections times 1920, which is the `town` value in `m.layerWidths`. All tiles must match each other at both edges, and no building may cross x=0 or x=1920 in any tile. Each tile adds about 4 MB of texture memory, because every tile in the strip is loaded at the same time. The street drawing (`street()` in `tools/riverside/scenery.py`) is shared by all tiles; its dash pattern repeats every 96 pixels, which divides 1920 evenly. When changing a layer's shape, make the y value at x=0 equal the y value at x=1920. For curves, also match the slope at both edges.
- The far and near mountain layers are two tiles each: `far` and `far_b`, `near` and `near_b`. Their strips hold A, B, A and slide by 3840 pixels (the `far` and `near` values in `m.layerWidths`). The B tiles must start and end at the same heights as the A tiles (470 for far, 560 for near) so the tiles join in any order. Only the A far tile can have Table Mountain, and only when `extras.table_mountain` is on. The README previews draw them as A, B, A, B across the street.
- Each layer is cropped to a horizontal band to save texture memory. The crop values in `CROPS` in the generator must match the `translation` and `height` of the matching strip in `components/MainScene.xml`.
- Layers must overlap with no gaps. A lower layer must reach below the top edge of the layer in front of it at every x position, or the sky shows through.
- The top of the river must start below the top edge of the hills, or the water shows above the hills, in front of the mountains.
- With `extras.table_mountain` on, the center far mountains are shaped like Table Mountain seen from Cape Town, based on a silhouette reference from the owner: Devil's Peak on the left, the flat top with steep cliffs, a dip, and Lion's Head on the right. All points on the flat top (`TABLE_TOP` in the generator) must have the same y value, so `snow_caps()` does not treat them as a peak; `far()` draws a flat snow band there in winter instead. `snow_caps()` skips peaks that rise less than `min_rise` (30 pixels) above a neighbor point, so small bumps such as Devil's Peak and Lion's Head get no snow cap.
- The sky is an 8 pixel wide gradient stretched to 1920 pixels. Keep it narrow.
- The clouds layer has one image for each level in `CLOUD_LEVELS` in `tools/riverside/scenery.py` (`few`, `scattered`, `broken`, `overcast`), named `clouds_<level>_<period>.png`. `cloudLevel()` in `MainScene.brs` picks the level from `cloud_cover` (a percentage from Open-Meteo, requested in `WeatherTask.brs`), and the weather code sets the lowest level so the sky matches the panel text. Overcast also uses the gray sky `sky_overcast_<period>.png` (the `skyGray` and `horizonGray` colors in `P`), hides the stars, and dims the sun and moon. `preview()` in `previews.py` copies this with its `clouds` option. Clouds that cross x=0 or x=1920 are drawn with `wrap()`, which draws the whole level three times, so overlapping clouds keep the same order on both sides of the tile edge. "few" is the original three clouds and is used before the first weather request finishes.
- The town crop starts at y=550 so the church cross and the courthouse clock tower fit. If anything in the town is drawn above y=550, it is cut off.
- Store sign text is drawn with `text()` in `tools/riverside/art.py`, which converts letters to shapes using the fonts in `tools/fonts`. It works with variable fonts and with fonts that have one weight. Do not use SVG `<text>` elements, because they depend on the fonts installed on the computer that runs the generator. To add a font, put the `.ttf` file and its license in `tools/fonts` and add it to `FONTS` and to the font list in README.md. `check_text()` reports letters a font cannot draw, and `config.py` uses it to stop the build with a clear message. Only use fonts with a license that allows this, such as the SIL Open Font License. Write non-ASCII letters as Python escapes (for example, `"Luke\u2019s"`).
- The generator writes the README preview images in `docs/` when it is run with `--docs docs`. They are committed and show the sample town. Run it after any art change so they stay current. `CARS` in `tools/riverside/previews.py` copies `allCars` in `MainScene.brs` and must be kept the same. The preview panel copies the `info` group in `components/MainScene.xml`.
- The car parked at the gas station is not part of the town image. The layout writes the center of the parking space, in strip coordinates, as `parkedCarX` in `town_config.json` (`gas_parking()` in `buildings.py`). `parkCar()` in `MainScene.brs` adds the car to `townStrip` there. If the gas station is in section A, it adds a second copy for the repeat of section A at the end of the strip. If the gas station drawing changes, update `GAS_PARKING`.
- Wall colors in `town.json` are day colors. `wall()` darkens them for dusk and night the same way the palette darkens `houseA`. Buildings without a color get one from `HOUSE_PALETTE`, `SHOP_PALETTE`, or `SCHOOL_PALETTE` in `config.py`, in order. The columned hall and the gas station canopy keep the palette colors.
- Car images do not include the wheels. Wheels are a separate image so they can spin. If a car's size or wheel positions change in `tools/riverside/sprites.py`, update the matching entry in `allCars` in `components/MainScene.brs` and in `CARS` in `previews.py` (`w`, `h`, `wheels`, `r`, and `bottom`).

## Seasons

- `currentSeason()` in `components/MainScene.brs` picks the season from fixed dates: spring from March 20, summer from June 21, fall from September 22, and winter from December 21. `m.seasonOverride` forces one season. With `seasons` off in the settings it is always summer. In the southern hemisphere the season is swapped (winter and summer, spring and fall).
- Season colors are in `SEASON_COLORS` in `tools/riverside/art.py`. Write only the day color. `season_palette()` makes the dusk and night colors by darkening the day color the same way the summer palette darkens that key. New keys that are not in `P` must be added to `SEASON_BASE_KEY` so they darken like an existing key.
- The kayaks beside the river (`extras.kayaks`) are drawn by `kayaks()` in the hills layer, at the positions in `KAYAKS`. They are on the grass, not in the water; if the river shape changes, check that they still are. They are not drawn in winter.
- Every scenery layer function takes `(p, season)`. Seasonal details (snow on roofs, pumpkins, flower boxes) use helpers such as `snow_flat()`, `snow_ridge()`, `pumpkins()`, and `flower_box()`, which return an empty string in other seasons.
- `SEASONAL` in `tools/generate_images.py` and `m.seasonalLayers` in `components/MainScene.brs` must list the same layers and seasons. Every town section has all four seasons; `init()` adds the town sections to `m.seasonalLayers` from the number of sections. Otherwise the scene asks for an image that does not exist.
- While snow is falling, `applyScene()` uses the winter images in any season. Falling leaves and fireflies are hidden while rain or snow is falling. Nothing falls in spring, as the owner asked. In fall, `onLeafTimer()` fades the leaves out and back in at random times (`m.leafOnMin` and the other leaf settings). The leaf animation keeps running while they are faded out, so when they fade back in, they are already partway down the screen.
- In winter the sidewalk is a plain snow-colored rectangle. Keep any repeating pattern on the street at a spacing that divides 1920, so it joins up at the tile edges.

## Scene behavior to keep consistent

- `m.cameraSpeed` must equal the `town` value in `m.layerSpeeds`. A car's on-screen speed is its `ground` speed minus the camera speed when it moves right and plus the camera speed when it moves left.
- `drive_on` in `town.json` (`driveOn` in `town_config.json`) sets the side of the road. With `"right"` (the default), the near lane moves right and the far lane moves left. With `"left"`, the directions are the other way around. `spawnCar()` in `MainScene.brs` and `preview()` in `previews.py` both follow it.
- `town.json` can turn cars off. `m.carDefs` holds only the cars that are on. The schema requires at least 2 cars.
- Special cars are cars from movies: the DeLorean (`delorean`), the time machine from the first Back to the Future movie, and Herbie (`herbie`), the Love Bug. They are listed in `special_cars` in `town.json` (`SPECIAL_CARS` in `config.py`, `specialCars` in `town_config.json`), not in `cars`, and none are on by default. Their entries in `allCars` have `special: true`. A special car waits longer before each trip (`m.specialFirstMin` and the other special settings in `MainScene.brs`), and `parkCar()` never parks one at the gas station. The README previews do not show them. Keep `special_cars` empty in the sample `town.json`, because the sample has no real references. Herbie's left image (`car_herbie_left.png`) is drawn again instead of mirrored, so the number 53 on the door does not read backward.
- Car ground speeds are ordered on purpose: the sports car fastest by a clear amount, then the DeLorean, then the sedan, then Herbie, then the VW buggy, then the van and Jeep, then the old truck slowest. Keep that order unless the owner asks for a change.
- Only one car uses a lane at a time so that faster cars never overlap slower ones. After a car leaves a lane, the lane stays empty for a random 1 to 10 seconds (`m.laneGapMin` and `m.laneGapMax`, in milliseconds), measured with `m.clock`.
- `placeAnimals()` in `components/MainScene.brs` puts the animals from the settings at random x positions on the sidewalk when the screensaver starts, anywhere along the strip. Section A appears twice in the strip, so an animal in section A gets a second poster at the same place in the copy at the end. Otherwise it would show in one copy and not the other, and it would appear or disappear when the strip repeats. Animal images are saved at the size they are shown, so the screensaver never scales them: `save_pet()` in `sprites.py` writes each animal at `PET_SCALE` (0.55) times its drawing, and `<name>_small.png` at `SMALL_PET` (0.65) times that. `pet_size()` in `tools/generate_images.py` reads the size from the image. A cat is about half as tall as a bike; keep animals smaller than bikes. An animal can also have a darker image for night, `<name>_night.png` (`save_pet(..., night=True)`); the gray cat has one, because it is close to the color of the sidewalk at night. The generator sets `night` for each animal in `town_config.json` when that image exists, `updateAnimals()` in `MainScene.brs` swaps it in at night, and the README previews use it. Each dog breed is one entry in `DOGS` in `sprites.py`, drawn by `dog()`; a new breed needs an entry there, in `PETS` in `config.py`, and in the schema.
- Bikes: `bicycle()` and `bike_frame()` in `art.py` draw an empty bicycle in a 60x46 box. Bikes on the sidewalk are drawn at `BIKE_SCALE` (1.25) and bikes on the hills at 0.7. As the owner asked, bikes are only in two places: in each `bike_rack` in town, and beside the radio station. Do not add bikes anywhere else. `sidewalk_bikes()` in `buildings.py` draws the bike rack bikes after the street, because they stand on the sidewalk. With `extras.bikes` on and a radio station, `radio_bikes()` in `scenery.py` draws the two bikes in `RADIO_BIKES` beside the station on hills tile A; they stand on the top of the near hill (`near_hill_y()`) and are not drawn in winter.
- The radio station (`radio_station` in `town.json`) is drawn on the hills layer by `radio_scene()` in `scenery.py`, at `RADIO_SCALE`, on the near hill at `RADIO_X`, with `tower_svg()` behind it. Its ground line is the lowest point of the hill under its base (`near_hill_y()`), so no part of the base is above the ground. The round tree at x=420 moves to x=130 when the station is there. The tower stands `TOWER_DX` pixels to the right of the station's center. Both of its legs (`TOWER_BASE_W` apart, times `RADIO_SCALE`) must reach the ground behind the building, so the whole building is in front of the tower. It is drawn before the near hill, so the hill covers the bottom of its legs. The hills are three tiles, `hills`, `hills_b`, and `hills_c` (A, B, C, A in the `hillsStrip`, sliding 5760 pixels, the `hills` value in `m.layerWidths`); only tile A has the station. `hills_b` has its own trees and kayaks in `TREES_B`, `ROUND_TREES_B`, and `KAYAKS_B`. `hills_c` has its own hill outlines (`FAR_HILL_C` and `NEAR_HILL_C`), no river and no kayaks, and its trees in `PINES_C` and `ROUND_TREES_C`. Every hill outline in `scenery.py` must start and end at the same heights and slopes as `FAR_HILL` and `NEAR_HILL` (see the comment above them), so the tiles join in any order. Each tile adds about 4 MB of texture memory. The README previews show tile A, B, or C by section number.
- The hills image starts at y=420, above the top of the hills, so the station's tower fits. `CROPS` and the `hills` strip in `MainScene.xml` must both use y=420 and a height of 490. The tower top must stay below y=420.
- The gazebo is drawn at `GAZEBO_SCALE` (0.8) of its full drawing by `gazebo_building()`. Its width in the layout is scaled the same way.
- The radio tower's red light is a separate image, `tower_light.png`, so it can blink. The generator writes its position in hills strip coordinates to `radioLight` in `town_config.json` (`radio_light()` in `scenery.py`), and `buildTowerLight()` in `MainScene.brs` adds it to both copies of hills tile A, with an animation like the airplane's tail light that runs at dusk and night. If the tower moves or changes size, the position follows it.
- Street lights (`extras.street_lights`) are drawn by `street_lamps()` in `buildings.py`, after the street, at `LAMP_X`. Their spacing, 480 pixels, divides 1920, so they stay evenly spaced across section edges. The gazebo's strings of bulbs and lantern are drawn by `gazebo_lights()`. Both are lit in the dusk and night images. `is_dark()` in `art.py` tells a drawing whether lights are on.
- A two-story house gets a second row of windows. The exact height of a house comes from its number, so houses next to each other are not all the same height.
- The airplane flies at the distance of the far mountains, so it is small (56x22 pixels) and its speed on screen is `m.planeSpeed` minus `m.layerSpeeds.far` when it flies right and plus it when it flies left. `m.planeSpeed` comes from the car scale (a Cessna is about 4 times as fast as the sedan) times 5/55, the far layer speed divided by the town speed. If the layer speeds or the sedan speed change, work it out again. Its `y` stays between 236 and 286 so it is above the mountain peaks and below the clock panel. Its posters are drawn after the far mountains and before the near mountains. It does not fly in rain, snow, fog, or thunderstorms, or at all when `airplane` is off in the settings.
- The airplane faces left with its own image (`plane_left_<period>.png`), not a mirrored node. The left image is drawn again instead of flipped because of the wingtip lights. Planes have a red light on the left wingtip and a green light on the right wingtip. A plane flying right shows its right side to the viewer, so the near light is green. A plane flying left shows its left side, so the near light is red.
- The clock panel stays in the top-right corner and the sun and moon stay in the top-left corner, as the owner asked. The panel moves between the positions in `m.infoSpots` with `infoMoveAnim`, which fades it out, moves it while it cannot be seen, and fades it back in. Do not set `m.info.translation` directly. The positions are small moves within the top-right corner, to protect TVs from burn-in. Keep each position fully on screen for the current panel width (580 pixels) and height (150 pixels), and away from the sun and moon positions in `applyScene()`. The README previews copy these positions in `preview()` in `previews.py`. The longest 24 hour clock value, "23:59", fits the clock label.

## Releases

README.md has the full steps in "Adding features and releasing". The rules:

- New features are made in this repository, on a `feature/` branch, and merged into `main` with a pull request. Other towns get them only when a new version tag is pushed.
- The Action runs the published image, not the code on a branch. To test a change before it is released, build a town with `python3 tools/build_town.py --config <town.json> --out out`.
- The owner pushes the version tags. This sandbox refuses tag pushes, so do not try to push one. In the pull request description, say which tag the change needs:
  - a fix that changes nothing for users: a patch version, for example `v1.0.1`
  - a new feature that existing `town.json` files do not need: a minor version, for example `v1.1.0`
  - a change that makes existing `town.json` files fail, such as renaming or removing a field: a major version, for example `v2.0.0`
- Avoid major versions. Prefer adding a new field with a default over renaming or removing one, so existing `town.json` files keep working.
- For a major version, change the image in `action.yml` from `:1` to the new major version in the same pull request. The publish workflow moves the `v<major>` git tag; repositories that use the old major version keep it until their workflow is changed.
- When a feature adds `town.json` settings, update the sample `town.json` here and in rorpage/riverside-town-sample (with a ZIP code there instead of lat and lon).
- The owner's family town is in rorpage/riverside-town-page-family. Both town repositories build with the published Action, so a `town.json` change that uses a new feature fails until that feature is released. Commit those changes in the town repositories, but do not push them yet. After the owner pushes the tag:
  1. Wait for the `riverside-town-roku-generator` publish run for the tag to pass, and check that the `v1` git tag moved to the same commit.
  2. Push the waiting commits to `main` in the town repositories. Each push starts their "Build my town" workflow.
  3. Check that each "Build my town" run passed and has both downloads, `riverside-town-roku` and `riverside-town-previews`. If a run fails, read its log and fix the cause.
- Do not put the family town's details (names, numbers, places) in this repository. They belong only in its own private repository.

## Branches

- Name a branch for a new feature `feature/<short-name>` (for example, `feature/util-scripts`). Do not use the `claude/` prefix for new features.

## Testing

The owner tests every change on a Roku. Do not test on a Roku, and do not mention Roku testing in replies or commit messages. If the generator changed, run it and check the previews in `build/` before committing. Also build a town with different settings (for example, one section with `table_mountain` on and the gas station in section A) with `tools/build_town.py`, to check that the change works for other towns.
